# Rust / rextendr scene-v1 benchmark spike

This isolated package implements the experimental scene-v1 JSON builder
through an R binding generated by rextendr. It depends on the same local
`crates/corrplot-core` library as the standalone CLI; matrix shape, labels,
missing values, finite values, and correlation semantics are validated by
that shared crate rather than by a copied Rust implementation.

The exported `build_scene_json_rust(labels, matrix, annotation)` function
preserves missing values as JSON `null`, emits cells in row-major order, and
uses the same geometry and style constants as the other candidates.

CI generates a disposable R package with `prepare-r-package.R`, compiles it
with the Rust stable toolchain, and installs it for the shared benchmark
harness. Generated package files and Cargo build output are not committed.

This remains an integration proof, not a production R-package migration. It
demonstrates one compiled validation operation shared with the CLI. CI verifies
offline source-package installation and `R CMD check --as-cran` on Linux,
macOS, and Windows, plus Windows binary installation without Rust on PATH.
Rust/Cargo 1.78 is the declared and CI-tested minimum. One CRAN-style NOTE
remains for Cargo vendor checksum/provenance metadata required by offline
builds; actual CRAN acceptance and production R migration remain unproven.

The 2026-10-31 Ubuntu 24.04 / R 4.6.2 run measured a 1,314,220-byte source
tarball and a 6.0 MB installed package (5.9 MB in `libs`). The installed size
exceeds rextendr's 5 MB caution and requires CRAN guidance before production
use. Controlled human maintainer time versus the C++/Rcpp path remains
unmeasured; existing effort ranges are planning estimates only.

The generated R Cargo package uses Cargo's standard release profile. A
controlled CI experiment compared it with a size-oriented profile
(`opt-level = "z"`, one codegen unit, and debuginfo stripping). That candidate
increased installed size on Linux and macOS and was therefore rejected; it
slightly reduced size on Windows. CI reports installed package, native
library, and Rust static-library artifact sizes on all three platforms and
prints the R integration's dependency tree. The R integration depends on
`corrplot-core` and `extendr-api`; it does not depend on or build the CLI
package. See
[`docs/rust-rextendr-size-optimization.md`](../../docs/rust-rextendr-size-optimization.md)
for measurements and follow-up analysis.


## Native-library symbol and section inspection (2026-10-31)

The offline package workflow now inspects the installed shared library after
installation and before building the source tarball. This is diagnostic only:
it does not modify the installed package, compiler flags, Cargo features, or
release profile.

Observed on the CI runners:

- **Ubuntu:** `corrplotngrustspike.so` is 6,207,880 bytes. GNU `size -A`
  reports 5,730,418 bytes across sections. The ELF contains substantial
  non-loadable DWARF/debug sections: `.debug_info` 1,137,254 bytes,
  `.debug_str` 1,914,653 bytes, `.debug_line` 478,397 bytes,
  `.debug_ranges` 538,080 bytes, and `.debug_aranges` 31,952 bytes.
  The `.text` section is 894,192 bytes. GNU `nm` enumerates 3,409 symbols;
  its largest entries include Rust standard-library backtrace/process
  functionality and `gimli`/object-reading routines, alongside the package
  wrappers and `corrplot_core` functions.
- **Windows:** the installed DLL is 1,164,288 bytes. LLVM objdump reports a
  `.text` section of 0xD7FB8 bytes and a `.rdata` section of 0x266E8 bytes.
  The available `llvm-nm` reports no symbols, so symbol-level conclusions
  cannot be drawn from this build.
- **macOS:** the installed library is 1,932,808 bytes. Apple `size -m`
  reports a `__text` section of 788,668 bytes and a `__LINKEDIT` segment
  of 770,048 bytes. The first inspection attempt used GNU-specific
  `nm` options unsupported by Apple's tool; the script was adjusted to use
  Apple's `nm -S` output and sort its size column. That corrected path must
  be confirmed by the next CI run.

These observations are facts about the current CI artifacts, not proof that
any particular symbol is unreachable or safe to remove. In particular,
backtrace and debug-information support may be intentional Rust runtime
behavior. The Linux DWARF sections are a concrete candidate for a separate,
controlled packaging experiment: compare stripping debug information from
the installed shared library while preserving symbols needed for runtime
behavior and diagnostics, then rerun offline install, R CMD check, and
cross-platform size measurements. Do not change release flags or strip
artifacts as part of this diagnostic PR.


## Isolated debug-information stripping experiment

The offline package workflow now runs
[`experiment-strip-debug.py`](experiment-strip-debug.py) against the
installed library only after the ordinary install and R smoke test succeed.
It creates a temporary copy, strips debug-only information from that copy,
compares the exported symbol names before and after, temporarily substitutes
the copy into the installed package, and reruns the R integration smoke test.
A `finally` block restores the original installed library byte-for-byte.
The generated source package, Cargo release profile, and production artifacts
are never modified.

- **Linux:** uses `objcopy --strip-debug` (or `llvm-objcopy`) and compares
  the ELF dynamic defined-symbol set using `nm -D --defined-only`.
- **macOS:** uses Apple `strip -S` and compares externally defined symbols
  using `nm -gU`.
- **Windows:** explicitly skips mutation for now. The current runner tooling
  has not yet been validated for a reliable PE/COFF debug-only strip plus
  matching export-table comparison; the ordinary Windows install and smoke
  tests still run.

The experiment fails if the exported symbol set changes or the post-strip R
smoke test fails. CI logs report the before/after native-library byte counts.
A smaller file alone is not sufficient evidence for a production change:
the source-tarball build and `R CMD check` continue after the experiment,
and the result must be reviewed across platforms before proposing any
production packaging modification.
